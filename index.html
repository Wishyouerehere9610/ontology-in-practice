Enterprise AI / FDE Field Notes

Ontology从一堆文档，到 AI 能理解并执行的业务世界

RAG 擅长找到文字。当任务进一步涉及统一对象、稳定口径、业务计算和受控写回时，企业还需要一层可治理的业务模型。

15-20 分钟阅读 适合 FDE / Agent 工程师 版本 2026.09

Ontology 的价值不在“把表改个业务名字”，而在将对象、关系、规则、函数、动作和权限放到同一个可治理的操作层中。

data → meaning → decision → action

01 / The problem

文档都在，答案为什么还会飘

老板问“供应商 A 的评分是多少”。同一个 Agent，上午答 85，过两分钟又答 92。数据未必丢了，模型只是不知道评分对象、指标口径和时间版本之间的关系。

没有 Ontology

把文档直接扔给 LLM

RAG 找回了几段相关文字，模型自己猜哪个数字是最终评分。

859278
有 Ontology

先定义业务对象和口径

供应商、材料、评分规则、生效日期和负责人都有明确关系。Agent 按口径查询，不需要临场拼凑。

问题不是“模型没看到数据”

真正缺的是业务语义和执行边界。企业需要告诉 AI：有哪些对象，它们如何关联，规则怎么算，什么人能做什么。

传统 Ontology 先卡在三类矛盾

人工共创太慢知识工程师和领域专家要反复画白板、争论命名和修改层级，整个周期往往以月计。
更新滞后于业务模型定义完成时，产品、流程和数据口径可能已经改变。
容易变成死模型如果没有连到 ERP、POS 等活系统，也没有持续维护机制，Ontology 很快就只剩静态文档。

02 / Definition

先分清三层，再谈 Ontology

本文使用的是广义的企业 Ontology。它从标准语义模型出发，连接知识图谱中的业务事实，再由平台补上函数、动作、权限和审计。三层可以组合，但不能混为一个概念。

标准定义 厂商产品语义 工程建议
Semantic Ontology

语义本体

用 Class、Property、Individual 和 Axiom 定义领域词汇、关系与约束。OWL/RDF 文件属于这一层。

Knowledge Graph

知识图谱

保存具体实体、事实和关系实例。生产系统还应记录来源、时间、版本与置信度。

Operational Ontology

企业操作层

把对象、逻辑、动作、安全和应用连起来，使人和 Agent 能在业务边界内查询、判断和执行。

Semantic

描述世界

  • Object Type：订单、仓库、客户
  • Property：状态、时间、服务等级
  • Link：订单属于客户，运输由承运商负责
翻译为
业务语言
Kinetic

计算和改变世界

  • Function：计算延误风险和影响范围
  • Action：改派承运商、更新 ETA
  • Policy：权限、确认、审计和回滚

数据库 Schema 主要描述存储结构。语义本体在它之上增加业务含义、关系和约束，企业平台再连接 Function、Action、权限与审计。Function 和 Action 不是 OWL 文件天然具备的能力，而是操作层提供的运行能力。

03 / Architecture choice

不是所有业务都需要 Ontology

先判断问题需要哪种结构，再决定是否建模。简单文档问答直接使用 RAG 往往更快。只有当对象、关系、规则和动作需要长期稳定复用时，Ontology 的建设成本才更容易得到回报。

问题类型优先方案判断依据
文档搜索、摘要和引用RAG目标是找到原文并生成带引用回答，不需要统一业务对象。
元数据过滤与稳定口径结构化 RAG文档已有清晰标签、时间、组织和版本，可以先约束检索范围。
实体关系穿透知识图谱或 GraphRAG问题依赖多跳关系，但暂时不涉及复杂写操作和治理。
跨系统对象统一与规则推理Ontology同一业务对象散落在多个系统，需要统一语义、约束和可解释判断。
业务写回、审批和审计企业操作层 + Agent任务会改变真实系统，需要权限、确认、幂等、回滚和责任边界。

出现这些情况时，先不要建设 Ontology

业务口径仍在频繁变化概念和流程尚未稳定，过早抽象会把团队拖进反复迁移。
数据与负责人没有到位没有事实源、访问权限和能调整流程的业务负责人，模型无法进入日常工作。
问题只需要检索如果 RAG 已能稳定解决，继续增加语义层只会提高维护成本。

04 / Construction routes

五种构建路线，不要只选最快的

下面是五种常见的实践路线，不是行业唯一分类。生产项目往往会混合使用，但上线前必须回到可验证的拆解流水线。

01

拆解流水线

NER 实体提取、关系识别、去重、结构校验、逻辑验证和存图分开执行。失败的事实只进日志。

工程量最大，可追溯性和稳定性最好。业务专家要定义验证规则。

生产首选
02

数据聚类

先用 NER 提取名词，Embedding 向量化后进行 AP 聚类，不需预设类别数量，最后让 LLM 命名并补关系。

新领域里很实用，但聚类质量会直接影响实体粒度。

探索未知领域
03

人机协同两步法

LLM 先产出概念清单和层级提纲，人工检查中间产物，确认后再生成 RDF/OWL 等标准格式。

审查点清晰，适合在一个迭代内做出可评审的 V1。

快速 V1
04

行业框架约束

用已有行业本体、类型规范或知识库约束 LLM，只允许它在既定语义范围内提取。

可减少自造概念，也方便对齐金融、医疗和电力等行业标准。

有标准的行业
05

端到端原型

一个 Prompt 让 LLM 从文本直接输出 Ontology，一个模型包办所有步骤。

速度快，但对 Prompt 极度敏感。只适合学习、演示和假设验证。

只做原型
不知道领域里有什么先用数据聚类或人机协同整理候选实体。
行业已有成熟标准优先复用行业框架，不让模型重新发明一遍。
准备接入生产用拆解流水线重做校验、版本、审计和回归。

构建时最容易忽略的五条经验

NER 是最容易出错的起点，类型、别名和实体边界错了，关系与层级会一路被污染。
关系提取要从实例三元组上升为本体关系，不能把文本中的偶然共现当成规则。
结构校验和逻辑验证是两层门禁，只有都通过的事实才能进入 Ontology。
端到端 Prompt 对措辞敏感，轻微改写就可能改变类型层级，不能直接当生产管道。
数据质量比数据量更重要。小而干净、约束明确的样本，往往比大量噪声文档更有用。

05 / Data pipeline

从原始文件到 Ontology，中间不能省

现实中的输入有 CSV、嵌套 JSON、数据库宽表、扫描 PDF 和手写记录。它们不会直接变成业务对象。真正费时间的部分，是接入、保留原始证据、解析、清洗和映射。

01连接

原样拉取，不在源系统前置改写。

02版本化存储

保留原始数据和每次变更，支持回溯。

03解析

处理 Schema、嵌套结构、OCR 和多模态识别。

04清洗映射

去重、校验、拆宽表，建立小而聚焦的实体表。

05对象化

把表、行、列和外键映射为类型、对象、属性和关系。

Dataset

结构化与半结构化的版本容器

保存表、JSON、XML 和每次更新记录。同步语义要区分 Snapshot 全量替换、Append 增量追加，以及 Update 和 Delete 对可变状态的影响。

MediaSet

非结构化文件与 AI 解析工作流

图片、音频、视频和 PDF 按 Schema Type 与 Primary Format 管理。结构化行通过 Media Reference 指回原文件，便于重跑解析和复核。

结构化

CSV / Database

推断字段类型，再过滤异常值、处理缺失值并形成干净表。

raw_flights → clean_flights
半结构化

JSON / XML

展开嵌套数组，把订单、乘客和多段行程拆为可关联的表。

booking.json → passengers + segments
非结构化

PDF / Image / Audio

OCR 与视觉理解先转为可读文本，再提取业务字段。人工复核不能省。

report.pdf → markdown → maintenance
Pipeline Builder

可视化变换

适合字段类型推断、过滤、去重、嵌套数组展开和常规映射，方便业务与数据人员一起审查。

Code Repository

代码管道

复杂规则、自定义解析和性能敏感处理进入 Python、Spark 或 Java 代码。这条路径要有版本、测试和可重现运行记录。

Media Reference 要保留原始证据

结构化后的每一行都应继续指向原始 PDF、图片或音频。当审计人问“这个结论从哪里来”时，系统可以回到原始页和原始版本。

数据进入本体前，还要过四道治理门

Entity Resolution

实体消歧

统一跨系统稳定标识、别名和合并规则。合同中的“甲公司”和 ERP 中的供应商编码必须能回到同一个业务对象。

Source Precedence

来源优先级

主数据、合同、业务单据和人工录入发生冲突时，系统要知道以谁为准，并保留被覆盖的事实。

Temporal Semantics

时间语义

区分业务发生时间、生效时间、系统入库时间和失效时间，避免用今天的口径解释昨天的业务。

Confidence and Review

不确定事实隔离

OCR 和模型抽取结果携带置信度与证据指针。未通过复核门槛的字段不能直接进入确定性规则。

增量更新要同时贯通三层

Source sync

只拉取新增和已变更的数据。

Pipeline

处理变更行，对可变状态去重并保留最新版本。

Ontology index

只刷新已改变的对象和关系。

批处理与用户实时 Action 之间还有时差。如果不定义合并与冲突规则，系统会同时看到新旧两个状态。

宽表拆解是 FDE 最耗时、也最值钱的判断

一张 ERP 宽表往往把订单、客户、商品和物流混在一起。它不能直接映射为一个 Object Type。FDE 需要判断哪些列属于哪个实体、哪些关系要建 Link、哪些概念根本不值得建模。

Domain Object Types

订单、商品、仓库等领域共识，跨客户可高度复用。

Source System Mappings

SAP、Oracle、自研系统的表与字段映射，可部分复用，但必须按实际导出结构校正。

Customer Extensions

客户特有字段、流程、动作和例外口径，属于项目现场定制。

Ontology 相比数据库 Schema 多出三项能力

全链路追溯从对象与属性回到干净表、变换步骤和原始文件。
受控写回推荐把 Action 请求、审批和结果写入独立记录，再由连接器更新事实源。这是一种生产架构模式，不是 Ontology 固有能力。
应用直接消费Agent 和业务应用面向对象、关系、函数和动作，不需要每个场景重写一套底层表 API。

06 / Operational layer

把“查数据”升级为“做业务”

一张干净表可以映射为一种 Object Type，每行是一个 Object，每列是 Property，表与表的关联是 Link。这一层能让系统看懂业务世界。Function 和 Action 则让系统可以计算并作用于这个世界。

01 / Object

业务对象

订单、承运商、仓库、客户和设备都应有稳定标识、属性与版本。

02 / Link

关系与追溯路径

Shipment 连到 Order，Order 连到 Customer。Agent 可以沿着关系查找 VIP 客户的延误订单。

03 / Function

专业业务计算

延误风险应由版本化函数读取历史、承运商履约率和天气，而不是让 LLM 凭感觉判断。函数是否确定，还取决于输入与依赖。

04 / Action

受控的业务变更

改派承运商、更新 ETA 或创建异常 Case。每个 Action 都有参数、规则、前置条件和副作用。

LLM 负责理解意图、选择函数和解释结果。

专业规则、数学计算和约束交给 Function。高风险变更交给带确认的 Action。这样才能把自然语言的灵活性与业务执行的确定性分开。

Function 要按依赖方式分别治理

Pure Function

固定输入，稳定输出

计算公式、规则和输入版本固定时可以直接回归。发布时记录函数版本、测试样本和缺失数据处理。

Model Function

带模型的不确定计算

记录模型、Prompt、上下文和评测版本。即使接口叫 Function，也不能把模型推断当成绝对确定结果。

External Function

依赖外部服务

天气、价格和业务 API 可能超时或变化。必须定义重试、降级、返回值校验和缓存边界。

Action 不能只定义一个按钮

执行前校验身份、对象范围、前置条件、风险等级和审批状态，并生成幂等键。
执行中处理超时、部分失败和重复请求，保留任务检查点，不把未知状态伪装成成功。
执行后回读事实源，记录副作用和审计证据。失败时执行补偿操作或转人工处理。

Action Layer 还需要三个辅助工具

Update Application VariableAgent 改变 Workshop 或应用页的状态，例如切换仓库范围后联动刷新。
Command Tool触发其他应用操作，例如在地图上标出高风险订单。
Request Clarification指令有歧义时先向用户确认对象和范围，不在不可逆操作上猜。

07 / Agent interaction

Context 是必须知道，Query 是允许探索

Agent 不应扫描全部 Schema，也不应直连底层数据库。每轮对话先注入已配置的背景，再让 Agent 在授权范围内查询对象和关系。

Retrieval Context

每轮都需要的确定信息

  • Ontology Context 绑定当前对象，或用 Vector Embedding 检索相关对象
  • 今日 KPI、当前角色和权限范围
  • Document Context 按场景使用全文模式或 Chunk 模式
  • Function-backed Context 汇总的客户 360 信息
VS
Object Query

根据问题临时探索

  • 过滤华南仓的延误优先订单
  • 沿 Link 追到客户与承运商
  • 对区域、状态和时间窗做聚合
  • 将关系追溯层数限制在可控范围

一条实用规则

确定性内容走 Context，允许 Agent 自主探索的内容走 Query。Context 塞得太满会浪费 Token 并干扰模型，Query 配得太窄则会让 Agent 查不到该有的信息。

Agent 与 Ontology 的五层交互

Context layer

系统确定性准备当前对象、文档片段、权限和必要背景。

Query layer

Agent 在许可范围内过滤、聚合、检查并沿关系继续追查。

Logic layer

调用封装好的 Function 执行风险计算、优化和业务规则。

Action layer

产生受控变更。高风险操作要求用户确认，低风险操作可按政策自动执行。

Governance

权限、数据范围、工具白名单、确认与审计贯穿前四层。

Tool Calling 怎么暴露给 LLM

Prompted Tool Calling

兼容性优先

工具说明作为 Prompt 的一部分交给模型，适用范围广，但参数约束和返回结构需要由应用自行校验。

Native Tool Calling

性能和 Token 效率优先

模型原生协议通常能提供更清晰的参数 Schema。是否支持多个或并行调用，仍取决于模型和 Runtime。系统只暴露已配置、已授权且与当前任务相关的能力。

一次端到端交互如何串起五层

01Context

系统确定性注入华南仓、权限和最相关的 Shipment。

02Query

按仓库和延误条件筛出 23 个候选订单，再沿 Link 补客户与优先级。

03Logic

调用风险函数，找出 5 个高风险订单并生成建议方案。

04Explain

LLM 带证据解释结果，询问用户是否执行。

05Action

用户确认后创建异常 Case，写回 Ontology 并记录审计日志。

08 / Governance

防幻觉不是加一句“不要编造”

对于企业 Agent，更可靠的办法是从结构上限制它能看到什么、能查什么、能调什么函数、能执行哪些动作。没有财务对象、没有财务权限、也没有相关函数时，Agent 应该根本接触不到营收数据。

调度员

只管三条线路

  • 查看三条线路的 Shipment
  • 计算延误风险并更新 ETA
  • 不能查看利润率
  • 不能改派承运商
区域经理

负责整个华南区

  • 查看全区概览与所有线路
  • 查询承运商绩效和利润
  • 确认高风险调度动作
  • 查看审计日志与操作结果
最小权限要同时作用于数据、查询、函数和 Action。

身份要从 WorkBuddy 或其他入口透传到查询与执行层。每次调用记录谁在什么时间查了哪些对象、调用了什么函数、请求了什么 Action、用户是否确认以及最终结果。

权限不是一个总开关

对象与字段同一个用户可能能看订单状态，但不能看成本、利润和个人信息。
Function能读取对象不等于能运行风险模型、价格计算或跨区域聚合。
Action查询权限不能自动升级为写权限。高风险动作还需要审批、额度和责任人。

外部 Agent 接入要分开“改结构”与“做业务”

Palantir MCP

面向开发者与 Ontology Builder

用于提议和修改 Ontology 类型定义，不直接写入业务数据。结构变更还要经过 Proposal Review 和人工审批。

Ontology MCP

面向外部业务 Agent

在 Application Restrictions 内读取对象、沿关系查询并执行 Action，但不能修改 Object Type 定义。

结构变化也需要发布流程

Owner & Proposal

每个对象、关系、函数和动作都有负责人。结构修改先形成 Proposal，不直接覆盖生产版本。

Review & Compatibility

评审影响范围，包括映射、查询、Function、Action、应用和历史数据。

Migration & Deprecation

需要迁移时定义双写或兼容窗口。废弃字段先标记，再通知依赖方，最后移除。

Rollback & Readback

发布后回读实际版本和运行行为。出现回归时能恢复结构、规则、连接器和配置。

09 / Production evidence

从 Demo 到生产，要有一条证据链

演示只能证明关键路径能跑。进入试点前，还要用代表性真实样本验证长尾问题、权限、失败恢复和人工接管。每次改动都要留下可以回放的版本与 Trace。

01 / Baseline记录现有人工流程或 Agent 基线。
02 / Samples准备代表性样本、坏例和边界案例。
03 / Trace记录解析、查询、函数、工具和决策过程。
04 / Taxonomy按数据、映射、规则、权限和工具归因失败。
05 / Candidate生成可比较的候选版本和变更说明。
06 / Gate用回归集判断是否达到发布门槛。
07 / Rollout限定用户、数据和自动化范围进行灰度。
08 / Readback回读实际加载版本、运行结果和回滚状态。

三个核心指标必须写清分子和分母

决策正确率

正确最终结论数 / 符合评测口径的样本总数。

证据完整率

正确引用证据的结论数 / 应提供证据的结论总数。

人工接管率

需要人工完成的任务数 / 进入试点的任务总数。

同时记录端到端延迟、单次任务成本、数据同步新鲜度、工具失败和回滚结果。每个指标都要注明基线、排除项、时间窗口、数据负责人和复盘频率。

工程建议

Shadow / ALT 负责把变化变成可发布证据

用同一批真实样本回放普通 RAG / Skill 基线与 Ontology 增强方案。分别观察场景识别、实体映射、规则命中、证据引用和最终决策，不把端到端分数当成唯一答案。

10 / Delivery playbook

一个可以真正开工的落地清单

Ontology 项目不应从“建全公司知识图谱”开始。先选一个决策频率高、数据可取、动作边界清楚的业务问题，再向外扩。

  1. 把业务问题写成可验收句子

    例如“在 30 秒内找到华南仓的高风险优先订单，给出原因和可选处理方案”。

  2. 圈定最小对象与关系

    只建与该决策直接相关的 Shipment、Order、Customer、Carrier 和 Warehouse。

  3. 建立原始数据到对象的映射

    宽表先拆分，非结构化材料先解析，每个结果都保留证据指针。

  4. 把专业判断写进 Function

    明确输入、计算方法、输出 Schema、缺失数据处理和回归样本。

  5. 为 Action 设定风险等级

    高风险操作要展示影响、成本和代替方案，用户确认后再执行。

  6. 用真实记录做端到端验收

    验证对象映射、关系追溯、函数结果、权限拒绝、确认流程、写回和审计日志。

  7. 建立发布与回滚门禁

    候选版本先跑回归和坏例，再限定范围灰度。失败时能够恢复模型、规则、Ontology、连接器和配置。

  8. 完成采用与资产收尾

    跟踪目标用户是否持续使用，并区分客户配置、行业扩展和可进入产品基线的稳定共性。

Definition of Done

每个关键字段都能追溯到原始记录。
实体别名、关系和版本有回归样本。
Pure Function 对固定输入给出稳定结果；Model 和 External Function 有独立评测与失败处理。
越权查询在数据层就被拒绝。
高风险 Action 未确认时不会执行。
所有查询、函数和变更都能在审计日志中还原。
数据同步新鲜度、延迟、成本、工具失败和人工接管可观测。
Prompt、模型、Ontology、Function、Action 和连接器都能版本化和回滚。
候选版本通过代表性样本与坏例的回归门禁。
试点用户持续使用，流程负责人确认业务结果和自动化边界。
客户定制、行业模板和公共产品能力有清晰边界。
